**The cursor is a real defect, and it is not about Enter.** Thirty to-do items typed into the sprint notes at 1440×900:

| | after 10 items | after 20 items | 0.7 s after typing stops |
|---|---|---|---|
| as shipped | caret **419 px below the fold** | **856 px below** | back in view |
| with `scroll-behavior: auto` | on screen, 878 px | on screen, 878 px | on screen, 878 px |

Chrome only, desktop and mobile; WebKit keeps the caret in view either way, which is why this survived being looked at. **The mechanism:** the browser scrolls the caret back into view on every keystroke, and `html { scroll-behavior: smooth }` makes it *animate* — so at typing speed each keystroke restarts an animation that never arrives. You type and you cannot see what you are typing. That is what "writing is not instant like Notion" means here, and it is the same declaration that made PF-9's scroll jump look like an application bug.

**Fixed:** `html:has(.ProseMirror:focus) { scroll-behavior: auto; }` — smooth everywhere else, off exactly while somebody is writing, and no JavaScript, because this is a state the document already knows. **Measured after, all three engines:** caret on screen before Enter and after it, `caretMoved: 0`, `stillOnScreen: true`, and the document moves **46–49 px** — one line, which is what following a caret looks like.

## Standing constraints for every PF pass

1. **Performance is not traded for polish.** `npm run budgets` must stay OK. Measured before and
   after this pass on the same isolated stack, one production build each: **217.4 → 217.9 / 220 KB
   total** and **77.6 → 78.0 / 110 KB own**, so PF-3, PF-5, PF-6, PF-7 and PF-9 together cost
   **0.5 KB** and the shell has **2.1 KB** of headroom. Any new client component is measured, not
   estimated, and any new surface that lives behind a click goes behind `next/dynamic` by default.
2. **Resilience.** Every new interactive path handles the network failing: a Server Action call is a
   `fetch` and a network failure *rejects* it, so `if (!result.ok)` never runs. Convert throws into
   results; rethrow `redirect()`/`notFound()` via `unstable_rethrow`.
3. **Responsive.** Phone is the base. Every change verified at 320 / 390 / 768 / 834 / 1024 / 1180 /
   1440 / 1920, light and dark, with zero horizontal overflow — and touch targets at 44px on a
   **coarse pointer** (a headless browser reports `pointer: fine` and will lie).
4. **The visual conformance work is not abandoned.** These sit alongside `08-GAP-MATRIX.md`'s open
   rows (V-D1/D3, V-D4a, V-D8–D11, V-F1, Phase 9, the idle save chip, the 27 `--canvas` hovers),
   not instead of them.
5. **Nothing is `done` without a command or a measurement in the Evidence column.**
6. **`npm run test` is green, and PF-2's red has a command of its own.**
   It was `480 passed / 1 failed` until 2026-08-28, and a permanently-red suite cannot tell "PF-2 is
   unbuilt" from "something new broke" — the same failure mode `scripts/gate.sh`'s header records.
   `tests/notion-roundtrip.test.ts` is excluded from `npm run test` by name and runs under
   **`npm run roundtrip`**, which still fails and still prints every field that drifted. That script
   is on `npm run gate` and its check is **inverted**: it fails the day the round trip starts
   passing, which is the day the exclusion comes out and PF-2 closes. Anything red in `npm run test`
   is now a real regression, with no exception to remember.

## Architecture decisions — 2026-08-29

**Full local-first: rejected.** Reasons above. Revisit only if the product gains real offline field
use, or a user count where the round trip stops being affordable. Neither is true for four people
at desks.

**Migrations: squash, but not yet.** 38 is not a scalability problem — it is a reset-time and
readability one, and it costs most in the E2E sweeps that reset five times. Squashing rewrites
history the hosted project has already applied, so the order is immovable: **real backup → hosted
caught up to local → squash → verify with `db dump --linked`, because `db diff` ignores grants.**
Squashing a database with no restore point is the single most dangerous thing on this list.

**Branch model: trunk-based, not testing/uat/production.** Three long-lived branches create
permanent merge debt and three things to keep in sync — for four people with ONE database that is
cost with no benefit. Instead: `main` is the trunk and is always deployable; work happens on
short-lived `feat/*` and `fix/*` branches that merge back through a PR CI runs; **Vercel's
per-branch preview deployments ARE the testing/UAT environment**, free, with their own URLs, and
they die with the branch; releases are tagged so a rollback has a name. **Known limitation, stated
not hidden:** previews point at the same hosted Supabase, so a preview is isolated in code and not
in data. A second free Supabase project could be a staging database later; it doubles the migration
work, so not now.

**PF-2's sub-item question is decided — option 2.** Notion has sub-items; Coditu has no item→item
relation, because invariant 1 makes a work item a leaf. Carry the parent's Notion page id on the
child in a column nothing in the app reads or renders, scoped as **migration-only with a removal
ticket filed at the same time**. Reason: during the parallel fortnight the team is still working in
Notion, so flattening their board is the one visibly damaging option, and "it will still be there
in a year" is answered by naming its expiry. `grouping` as a lossy stand-in was rejected — it
overloads a field the team uses for something else, which is worse than an inert column.

**R2 is abandoned, not blocked.** §4 question 2 of `docs/09-BACKUP-PROPOSAL.md` chose Cloudflare
R2. Its allowance is free; its account requires a billing profile with a payment method, which
Mohamed refused. T0.2 replaces it with a dedicated **private GitHub repo** for the encrypted
archives plus **Google Drive via rclone** as the off-provider leg.
